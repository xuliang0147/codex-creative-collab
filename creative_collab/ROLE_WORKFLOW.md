# 创意协作角色工作流

## 固定角色

当前固定角色为编导、拍摄、平面、剪辑、即梦，不动态创建临时 Agent。每个编导有独立的执行团队；不能复用另一编导的执行任务。下方保留现有业务门槛，尤其“至少两条成片”仍是后端限制，不因上传备份而改变。

| 角色 | 责任 | 写入目录 | 主要交付 |
| --- | --- | --- | --- |
| 编导 | 建项目、脚本、调度、审核、批准、完成 | `01_编导/` | 脚本、审核意见、项目结论 |
| 拍摄 | 镜头拆解、素材检索、缺口确认 | `02_拍摄/` | 素材匹配表、待拍清单 |
| 平面 | 封面、贴片、AI 画面、成品图 | `03_平面/` | PNG/JPEG 成品及来源说明 |
| 剪辑 | 素材齐套、工程组织、差异化混剪、返工 | `04_剪辑/` | 至少两条不同内容的可播放 MP4 |
| 即梦 | 生成参数、积分核验、AI 视频生成及记录 | `04_剪辑/即梦/` | 已核实的生成产物与参数记录 |

每个角色只能登记自己目录内的 artifact。SQLite 是权威状态，项目目录和 `00_协作账本/` 下的 Markdown 是可读镜像。

## MCP 生命周期

每一次 task、handoff、revision 派发都必须完成以下步骤，不能把“已生成消息”当成“已发送”。

1. 发送方调用 `dispatch_prepare`，取得目标 `thread_id`、`host_id`、消息正文和一次性 `prepare_token`。
2. 调用 Codex 线程消息能力，把返回的 `message` 实际发到指定线程；保存外部系统返回的 `submission_id`。
3. 发送成功后调用 `dispatch_mark_sent`，提交原 `prepare_token` 和真实 `submission_id`。
4. 接收方看到消息并回传该 `dispatch_id`，由接收方调用 `dispatch_mark_received` 登记回执。若 `codex exec resume` 子任务因沙箱只读无法写默认 SQLite，发送方控制层只能在核对目标 `thread_id`、真实 `submission_id` 和包含同一 `dispatch_id` 的目标线程回复后代登记回执。
5. task 派发还必须由接收角色调用 `task_accept`；handoff 和 revision 的接收状态由回执推进。

未绑定真实线程时，`dispatch_prepare` 必须失败；外部发送失败时不得调用 `dispatch_mark_sent`；没有接收方真实回复时不得补 `dispatch_mark_received`。控制层代登记只处理 SQLite 写权限，不代表控制层可以代做目标角色工作。项目完成前，所有 dispatch 必须脱离 `pending` 和 `sent`。

子线程若遇到 registry 只读，必须继续完成本角色文件，并把内部回执交给发送方控制层代登记。不得把这些技术信息写进面向任务发起人的业务汇报。`blocked` 仅用于本角色自身验收交付无法完成；发现素材缺失或需求不清时，角色必须先用专业反馈单交回编导，由编导统一登记并向任务发起人确认。

当前 service 在 task 的 `dispatch_mark_received` 内已经原子地把任务置为 `accepted`。因此随后显式调用 `task_accept` 时，若只返回 `got received`，必须回读任务状态：状态确为 `accepted` 才能视为重复确认；其他错误一律中止流程。

## 标准生产流程

1. 编导创建项目后，先向任务发起人逐项确认目标、人群、平台、时长、交付版本、已有素材、创意方向、限制条件和待确认问题。需求未确认前禁止向其他角色派发。
2. 任务发起人确认后，编导完成《编导脚本任务单》，每个镜头必须写明时间码、画面、口播、字幕、素材来源、当前状态、责任角色和验收标准，再派发给拍摄和平面。
3. 拍摄先检索已有素材并按《拍摄反馈与补拍需求》逐项核验。无论素材齐套还是存在缺口，结果都只交回编导，不直接联系任务发起人，也不直接交给平面或剪辑。
4. 平面按《平面反馈单》把完成项、缺口和需要确认的内容交回编导，不直接联系任务发起人或剪辑。
5. 编导汇总所有反馈。若有素材缺失或需求卡点，用自然语言和表格一次性告诉任务发起人需要补什么、怎么拍、上传什么；在任务发起人完成前禁止派发剪辑、创建剪辑工程、预剪或导出。
6. 任务发起人补充后，编导组织拍摄复核并逐项关闭待补事项。只有全部关闭且编导明确“素材齐套，可以剪辑”后，才能派发剪辑。
7. 剪辑生成两条内容差异明确的可播放 MP4，并按《剪辑交付反馈单》交回编导审核。
8. 审核不通过时，编导只把明确的成品质量问题按责任退回。外部素材未到不能归责给任何制作角色。
9. 责任角色保留旧文件并提交新版本。问题解决后由编导批准和完成项目。

## 单一沟通入口

- 任务发起人只和编导任务对话。只有编导可以发起用户确认和素材补充请求。
- 可以同时注册多个编导任务并并行负责不同产品。每个项目固定绑定创建它的编导，所有角色反馈按项目回到对应编导。
- 新编导默认追加注册，不覆盖旧编导。只有任务发起人明确说“替代/替换旧编导”时，才允许迁移旧绑定。
- 拍摄、平面、剪辑有任何问题，都必须先形成专业反馈单并交回编导。
- 编导对任务发起人的回复只说：当前进度、需要确认或补充的内容、完成后会继续什么。
- 除非任务发起人明确要求排障或审计，回复中不得展示内部编号、目录路径、数据库、接口、命令、程序状态或原始报错。

## 审核退回规则

- 只有编导可以提交审核、发起返工、批准和完成项目。
- `revision_required` 至少包含一个问题；每个问题必须引用本项目 artifact。
- `responsible_role` 必须与 artifact 的所属角色一致，不能把剪辑问题退给平面。
- 一次 `revision_return` 只处理一个 `issue_id`，不能按角色批量关闭问题。
- 返工不能覆盖旧文件；新 artifact 通过 `supersedes_artifact_id` 建立修订链。
- 有 `open` 或 `returned` 问题、少于两条有效成片、存在未送达 dispatch 时，禁止批准或完成。
- 外部素材或用户输入未到，不是已登记 artifact 的质量缺陷，也不是剪辑问题。
- 任何用户确认或素材补充事项保持开放时，系统必须拒绝剪辑派发、剪辑接收、剪辑制作和剪辑交付。
- 等待外部输入时不得创建剪辑预览、占位成片或返工单。素材补齐并由编导关闭事项后，才允许首次派发或重新派发剪辑。

## 当前不包含

- 临时角色、动态 Agent 编排和自动扩缩容。
- 通用的自动重试和完整异常恢复。已有可选常驻派发/文档队列与限定条件的报告恢复，不代表任意失败都能自动修复。
- 自动拍摄、自动生成业务可发布成片、自动上传抖音或投放千川。
- 复杂 RBAC、远程多租户、云数据库、高可用集群和 Web 管理后台。
- 自动理解所有素材语义、版权审查、合同审批和对外发布审批。
- 删除旧版本或自动清理项目文件；V0.1 保留修订审计链。

## 剪辑标准

编导和剪辑读取单独安装的 `creative-video-editing` skill。参考片复刻应核查结构、字幕效果、关键音效和节奏，不能仅交普通口播字幕。标准接入与当前后端限制见 `docs/剪辑标准接入.md`。
