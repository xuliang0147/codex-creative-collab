# 团队隔离与任务恢复

## 按编导固定团队

项目保存 `owner_thread_id` 和 `owner_host_id`。`creative_director_teams` 记录编导团队，`creative_team_bindings` 将剪辑、拍摄、平面、即梦分别绑定到独立真实任务。

- 同一个执行任务只能属于一个编导和一个角色，编导不能兼任自己的执行任务。
- 执行任务交付回本项目编导，不以最近活跃编导或全局默认编导代替。
- 缺失团队、角色绑定或编导主机不匹配时失败关闭，不悄悄使用旧公共任务。
- 注册后的旧全局执行绑定不再接收新派发；历史已发送和已接收记录保留。
- 旧的未发送派发和准备缓存失效，必须重新准备，不能重复利用旧 prepare_token。

代码在 `team_routing.py`，接口为 `director_team_register`、`director_team_list`、`project_route_get`。隔离测试使用虚构任务，不含生产 ID。

## 进度说明不能冒充成片

`task_resume_from_report` 仅修复剪辑任务误把控制/进度报告作为交接，导致任务进入 submitted、项目进入 director_review 的情况。

必要条件包括：

1. 当前任务为本项目仍有效的所属编导，且主机匹配。CLI/MCP 额外校验 `CODEX_THREAD_ID`。
2. 被恢复对象是编导交给剪辑的任务，当前状态仍允许恢复。
3. 报告属于最新、已接收的剪辑交接，原编导确实收到了对应派发。
4. 所有报告产物登记完整、内容指纹未变，是允许的控制/进度报告，不是成片。
5. 未产生正式审核/返修记录，也不能恢复已批准或已完成项目。
6. 同一交接只能恢复一次，同 request_id 重试保持幂等。

恢复只把任务回到 in_progress、项目回到 editing，并写入追加式恢复审计，不删除历史、替换视频、重新绑定团队或自动宣称完成。恢复后的下一步仍需由原编导交给原剪辑执行。

这不是通用“强制解锁”工具，不适用于任意卡住任务。真实剪辑质量问题仍用审核和返修链处理。
